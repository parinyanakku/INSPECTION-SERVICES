# ProElite Security Protection — phase 1

## What is enforced
- Explicit production minification, no production source maps; check newly generated code and tracked files for a limited set of high-confidence credential signatures before deployment. Reports only file names and categories, never credential values. Do not treat a pass as a complete security audit.
- Remove the two imported pre-license HTML prototypes from the source branch and each archived version served by Pages. Existing versions retain their normal entry points and customer-report viewers. Map files are removed from archived published snapshots; the old archive is checked for filenames, not a full content secret scan.
- Do not alter local project data, Google Drive sync, image processing, account storage, native installer distribution or customer report encryption in this phase.

## Exposure remaining
The source repository and previous Git history are public. Deleting a file from main or current Pages is not erasure of past commits, forks or downloaded copies. The public JS bundle is readable and can be reverse engineered even when minified. Existing AI prompts, models and local business logic are still in client code; an authenticated gateway does not make those prompts private. API keys entered by buyers currently reside in their own workspace, not protected by code minification. Public client keys are not credentials that confer admin access.

## Next phases (do not disable production access before validation)
1. Owner creates or authorizes private source repository and connects approved hosting; migrate code, build workflows, deployment secrets, archive strategy. Preserve current domain and OAuth origin, test side by side, plan redirection and rollback. Verify permissions and confirm that only static intended assets are public before closing the old repository. GitHub connector currently cannot change repository visibility/create repositories.
2. Full history/artifact secret review with approved scanner, rotate any confirmed exposed credentials, verify backend access controls and storage policies using representative non-admin and admin accounts. Never move buyer BYOK keys to a server without consent.
3. Move valuable new algorithms and prompts to an authorized server endpoint after private source is established. Keep only public UI, inputs and output schema client-side. Preserve existing offline/manual features; rate limit endpoints atomically and test bypass/parallel requests.
4. Native per-device cryptographic enrollment, server-side authorization, trusted signing and signed updates. Do not rely on browser user-agent checks or embedded WebView alone. Test Google OAuth, account isolation, local data migration, camera and exports on all platforms. No native-only enforcement before verified rollout.
5. Keep customer reports publicly accessible only through their existing authorized links; maintain owner-only installer distribution and revoke compromised sessions/devices. No paid services without owner approval.

No guarantee of preventing reverse engineering. No secrets or signing keys in Git.

## Phase 2: live license and gateway controls
The license and administrator lookup functions use caller permissions and the existing own-license RLS policy rather than elevated permissions. Admin management RPCs still require an active administrator and retain necessary privileged execution. The report AI gateway (non-Gemini providers) consumes an atomic database-backed quota of 30 requests per account per calendar minute, including model listing and invalid bodies after authorization. The counter is private, with one row per account. Local quota rejection is HTTP 503 (not provider 429), so existing automatic fallback cannot trigger another potentially billable provider. Direct Gemini, image analysis and offline/manual tools are unchanged; this is not a global API quota or a spend limit. The quota RPC intentionally uses narrowly scoped SECURITY DEFINER for private counter updates, with auth.uid and license checks. Existing data and download permissions are unchanged. Database tests use actual representative account roles without returning identifiers or retaining quota test rows. No new AI provider calls are required for these checks. The private source migration and native-device restriction remain pending.

## Phase 3: authenticated test-build integrity
The existing main-branch GitHub OIDC upload now checks an independently calculated SHA-256 and stores a private manifest with digest, byte count and verified commit. The server verifies the bytes again when serving a test package and the admin client checks the digest before allowing Save. Old test packages without a manifest are intentionally unavailable until rebuilt. This is integrity/provenance via the existing trusted CI and TLS boundary, not an independent publisher digital signature, runtime anti-tamper, or signed updater. Approved distribution remains unchanged and unsigned candidates remain unapproved. The Windows installer records the chosen folder for maintenance and uninstall; CI checks both default and custom paths. Private source, native device verification and signing still require further work.

## Phase 4: Windows device proof pilot
Admin-only test in the installer dialog in native Windows. CNG creates a per-Windows-user P-256 signing key with non-exportable policy. Only the public coordinates and signature are returned, and the native handler accepts only the fixed domain-prefixed challenge from the workspace origin. Supabase authenticates the user and admin license, issues a two-minute random challenge, verifies ECDSA, consumes the challenge atomically, and stores a fingerprint in a private table. Service-role-only RPCs and a one-challenge-per-user limit prevent direct buyer writes. The pilot proves possession of a key, not that the calling software is genuine or hardware-backed; an administrator could register another software key. No device enforcement, attestation, buyer registration or revocation UI yet. Android/iOS native key integrations and actual device testing remain pending. The old web workspace and all report/Drive behavior are unchanged.
